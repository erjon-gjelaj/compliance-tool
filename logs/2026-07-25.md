## Task 006 — Nav, smooth scroll, footer

The nav is a flat row of About / FAQ / Contact that stays visible at every
width. No hamburger, no dropdowns — three short labels fit on a 375px phone
with room left, and hiding four links behind a button would be ceremony for
its own sake. "Free gap check" is gone from the nav as instructed; it survives
as a footer link, since from `/about` there still needs to be a route back to
the form.

The link list now lives in `src/lib/nav.ts` and is read by the header, the
footer, and the sitemap. Adding a page is one line in one file rather than
three edits that drift.

Header and footer moved out of `page.tsx` and into the root layout. Otherwise
every new page would have had to remember to include them, which is exactly
the kind of thing that gets forgotten on page five.

Smooth scroll is CSS `scroll-behavior` on `html`, not JavaScript, wrapped in
`prefers-reduced-motion: no-preference`. It costs nothing, works on a plain
anchor, and anyone who has told their OS they want less motion still gets the
instant jump.

The footer now carries the wordmark, the ISN/Avetta disclaimer, a page list, a
contact block, a tick rule, and a copyright line.

**One thing worth knowing:** the copyright year is baked at build time, because
every page here is static. It advances on the next deploy, not at midnight on
1 January. The alternative is reading the clock in the browser, which costs a
hydration mismatch and a client bundle for one number. For a site that
redeploys on push this is the right trade, but it does mean a site left
undeployed for a year will show a stale year.

## Task 008 — Typography audit

The audit turned up more than stray fonts, so I fixed the underlying cause
rather than just checking the new pages.

Heading sizes were ad-hoc utility strings repeated per heading
(`font-display text-3xl leading-tight font-semibold tracking-tight …`), which
is how a fourth heading size quietly appears on page five. The scale now lives
in `globals.css` next to the existing `.tag`: `.type-h1`, `.type-h2`,
`.type-h3`, `.type-label`, `.type-lede`, `.type-body`. The two large steps are
fluid via `clamp`, replacing the old `text-4xl / sm:text-5xl / md:[3.4rem]`
ladder with one definition.

Two things it caught:

- Two near-identical label sizes had drifted apart — 0.95rem in the hero card,
  0.875rem on the form labels. Merged into one `.type-label`.
- The primary button style was copy-pasted in three places (hero CTA, form
  submit, contact page). Consolidated into `.btn-primary`, which is how three
  buttons end up subtly different otherwise.

Verified in the browser at 375, 768 and 1280px across all four pages: only
Bricolage Grotesque, IBM Plex Sans and IBM Plex Mono compute anywhere, with no
system-font fallback; `h1` renders identically at 54.4px and `h2` at 36px on
every page; and no page overflows horizontally at any of the three widths.

The wordmark keeps its own size rather than using `.type-h3`. It is a mark, not
running type, and it should not move if the heading scale is retuned.

## Task 009 — Tagline options

Drafted against the positioning in `business-model.md` — the externally

1. **"Find the safety paperwork missing from your ISNetworld or Avetta file"**

5. **"You were told to get prequalified. Start here."** — the trigger event in

   like an ad headline rather than a line that sits under a wordmark for years.
6. **"Four questions. Then a list of what your file still needs."** — describes
   the actual mechanic and the low commitment. Honest and unglamorous; too long
   for a tagline, would work as a hero subhead.
7. **"Templates don't know your trade."** — the DIY contrast, and true. But it
   is an argument rather than a description: nobody learns what we do.

**What I did with them.** Rather than force one line to do two incompatible
jobs, I split the constant in two:

- `SITE_SLOGAN` is new, and defaults to **option 2**. It is for places with no

## Task 012 — One typeface everywhere

The site was running three families: Bricolage Grotesque for headings, IBM
Plex Sans for body, IBM Plex Mono for the small uppercase labels. That is now
one family — Bricolage Grotesque — for everything.

**Which one, and why.** You said "one consistent font" without naming it, so I
picked. Bricolage is the face already carrying every headline, so keeping it
preserves the identity you have already seen and signed off on; going the
other way, to Plex Sans, would have kept body copy comfortable but made the
site look like every other technical SaaS page. The tradeoff is that Bricolage
is a grotesque with some character in it, and the FAQ has long stretches of
body copy set in it now. It is designed to work at text sizes and it reads
fine at 0.95rem, but it is a livelier body face than Plex was. If it grates
when you look at it, swapping the whole site is one line in `layout.tsx` plus
the matching `--font-sans` in `globals.css`.

The labels that used to be Plex Mono now use the same family at regular weight
with wide letter-spacing and uppercase. That treatment, not the mono face, was
what made them read as technical annotation, so the effect survives.

I deleted `--font-display` and `--font-mono` rather than aliasing them to the
same value. Aliasing would have let a stray `font-mono` keep working while
meaning nothing; deleting them means such a utility drops to a system stack
and is obvious in review. All existing usages were removed — verified nothing
matching `font-mono|font-display|plex` remains in `src/` outside comments.

**Note this contradicts CLAUDE.md**, which asks for a characterful display face
paired with a clean body face. Your instruction is newer, so it wins, but the
file still says the old thing and is worth updating if this is permanent.

Verified in the browser: every text-bearing element across all four pages
computes Bricolage Grotesque — 252 elements, no system fallback anywhere. The
built home page now references one font file instead of three.

**The OG card too**, as you asked. It had been loading Bricolage for the
headline and Plex Mono for the strapline; both are Bricolage now, at 400 and
700. That change had a trap in it: with only one weight registered, Satori used

## Task 014 — certloop.net

`SITE_URL` now falls back to `https://certloop.net` and `CONTACT_EMAIL` is
`hello@certloop.net`.

**One ordering trap worth reading before you deploy.** The fallback pointing at
the real domain means that if `NEXT_PUBLIC_SITE_URL` is left unset on Vercel,
the first deploy publishes canonical URLs, a sitemap, and OG tags all claiming
`certloop.net` — before that hostname resolves to anything. Search engines
would be told the authoritative copy of every page lives at an address that
does not answer.

So: keep `NEXT_PUBLIC_SITE_URL` on the `*.vercel.app` origin until the domain
is attached and actually serving, then change it in the same pass. `DEPLOY.md`
section 4 is rewritten with the full order, including deciding whether `www` or
the apex is canonical and redirecting the other rather than serving both.

`hello@certloop.net` still has to be created. That is now possible where it
was not before, and it matters: the Contact page, the FAQ, and the form's
success panel all tell people to use it.

## Follow-up — NEXT_PUBLIC_SITE_URL set on Vercel

You set `NEXT_PUBLIC_SITE_URL` to `certloop.net`. Written that way — without a
scheme — that would have **failed the Vercel build outright**, not degraded
quietly: `layout.tsx` passed the raw value to `new URL()` for `metadataBase`,
and `new URL("certloop.net")` throws.

`SITE_URL` now normalises the value instead. A missing scheme gets `https`,
`.origin` strips any trailing slash or path, and something genuinely
unparseable falls back rather than taking the build down. Checked five input
forms — `certloop.net`, `https://certloop.net`, either with a trailing slash,
and `www.certloop.net` — all resolve to a clean origin. Then ran a real build
with the bare value and confirmed the sitemap, robots, and canonical all emit
`https://certloop.net`.

**Still worth acting on:** that value is ahead of the DNS. Until the domain is
attached in Vercel and serving, the deployed site answers on `*.vercel.app`
while telling search engines its canonical home is `certloop.net`. The site
works fine — the risk is purely that crawlers get pointed at a hostname that
doesn't resolve. Either attach the domain promptly or park the variable on the
`*.vercel.app` origin until you do. `DEPLOY.md` step 4 has the attach order.

## Deployed — task 005 closed, and two things the live site showed

You confirmed the domain is attached and a production form submission landed
in Supabase. That was the one check that mattered, since the page is static
and a green build proves nothing about the form path. Task 005 is done.

I checked the live site rather than take it on trust, and all four pages, the
generated OG image, the favicon and the sitemap return 200. Two things came
out of that check. Neither blocks anything and neither is a code change, but
both would have gone unnoticed from the repo alone.

**The apex redirects to `www`, and the canonical doesn't know.**
`https://certloop.net` 308s to `https://www.certloop.net`, which is what
actually serves. `NEXT_PUBLIC_SITE_URL` is the apex, so every canonical link,
every `og:url`, and all four sitemap entries name a hostname that immediately
redirects somewhere else. Not fatal — Google usually follows it — but you are
telling crawlers the authoritative copy lives at a URL that doesn't serve it,
and your sitemap disagrees with your served origin. Fix is one setting either
way: make the apex primary in Vercel, or point the variable at `www` and
redeploy. Both written up in `DEPLOY.md`.

**Cloudflare is in front of Vercel and is rewriting `robots.txt`.** Every
response carries `server: cloudflare`, and Cloudflare's managed robots feature
is prepending a `Content-Signal` block that disallows `GPTBot`, `ClaudeBot`,
`CCBot`, `Google-Extended`, `Bytespider`, `Amazonbot`, `Applebot-Extended` and
`meta-externalagent`.

This one is worth reading twice, because **it is not in this repo**. Nothing
in `src/app/robots.ts` blocks anybody — reading the source tells you the
opposite of what crawlers actually get. It is a Cloudflare default. Ordinary
search is unaffected (`search=yes`, `Allow: /`), so indexing is fine; but if
you want the site eligible for AI answer surfaces, that is a Cloudflare
dashboard setting. A side effect: the apex `robots.txt` drops our `Sitemap:`
line entirely, while the `www` one keeps it — fixing the apex/www split fixes
that too.

`CONTACT_EMAIL` is `info@certloop.net`. Still worth sending one message to it
from outside to confirm delivery, since four places on the site point there.
