# CertLoop — Domain & System Specification

Replaces the previous brief. This is the subject-matter model the product needs to
represent. Treat everything here as **data and configuration, not hardcoded logic** —
requirement lists are per-client, per-trade, and change over time.

Verify against a live ISN/Avetta account before shipping anything user-facing. Sources
disagree on weightings and exact lists; where they do, this document says so.

---

## 1. The six evidence categories

Every prequalification platform (ISNetworld, Avetta, Veriforce, ComplyWorks, BROWZ,
Appruv, CanQualify, Highwire) evaluates the same six things under different packaging.
Model these once and every platform becomes an export.

| # | Category | ISN name | What it is |
|---|---|---|---|
| 1 | Written programs | RAVS | Company-specific written safety programs, reviewed by a human |
| 2 | Statistics | Q&A (Quantitative & Qualitative) | TRIR, DART, LTIR, EMR, hours, fatalities, citations — 3-year history |
| 3 | Recordkeeping | OSHA logs | 300, 300A, 301 for current + prior 3 years |
| 4 | Insurance | COI review | GL, WC, Auto, Umbrella — limits and endorsements per client |
| 5 | Questionnaire | MSQ / MQ | Several hundred to a few thousand questions, general + client-specific |
| 6 | Training | Training documents | Rosters and sign-in sheets proving employees were trained on submitted programs |

**The cross-check is the whole game.** Reviewers reject for *inconsistency between
categories* more than for absence. Reported TRIR must reconcile with the 300A. MSQ
answers must match the uploaded programs. Training claims must match rosters. Build the
data model so cross-category contradiction is detectable, because that is the single
most valuable thing this product can tell someone.

<cite index="94-1">MSQ responses trigger RAVS requirements — updating the MSQ can produce new RAVS tasks within 24 hours.</cite> Model that dependency edge explicitly.

**Grade weighting is client-specific.** Published estimates vary widely: <cite index="95-1">one consultancy puts the MSQ at roughly 10–15% of the final grade and RAVS at 30–40%</cite>, while <cite index="88-1">another says the written-program section can account for up to 95% of the compliance score</cite>. Do not hardcode a weighting. Store it per hiring client, default to unknown, and never display a predicted grade.

## 2. Core entities

```
Company
  ├─ legal_name, dba, ein, address, states_worked[], employee_count_band
  ├─ naics[], trade_codes[], scope_of_work[]        # drives requirement generation
  ├─ competent_persons[]  (role → named person)
  └─ safety_leadership[]  (name, credential: CSP/ASP/CRSP/CHST/OHST, cert number)

Platform            # ISNetworld, Avetta, Veriforce, ComplyWorks, BROWZ
  └─ subscription_status, account_id, next_revalidation_date

HiringClient        # Chevron, ExxonMobil, Dow, BASF, Valero, USACE, plant, GC
  ├─ platform_id, connection_status
  ├─ grade_current, grade_threshold, grade_history[]
  ├─ deadline (date the client wants approval by)
  └─ requirement_set_id

RequirementSet      # generated from trade × scope × platform × hiring client
  └─ Requirement[]
       ├─ category (1–6 above)
       ├─ key            # e.g. "program.confined_space", "stat.trir.2025"
       ├─ status: missing | draft | submitted | under_review | accepted | rejected | expired
       ├─ due_date, submitted_at, reviewed_at
       └─ evidence_ids[]  → Document[]

Document
  ├─ file, content_hash, mime, pages
  ├─ extraction: {method: text|ocr|manual, confidence, text, page_map}
  ├─ doc_type (classified): program | coi | osha_300 | osha_300a | emr_letter |
  │           training_roster | cert | license | msq_export | other
  ├─ effective_date, expiry_date, issuing_party
  └─ version_group_id, version_n

Program             # a written program, generated or uploaded
  ├─ program_key (see §3), version, status
  ├─ questionnaire_response_id
  ├─ required_elements: {element_key: present|missing|weak}   # see §4
  ├─ answer_key[]     # see §5
  └─ outputs: docx, pdf

Request             # paid or unpaid human work
  └─ type: rejection_fix | program_write | full_setup | review
     status: requested → quoted → accepted → in_progress → delivered
```

## 4. Required elements — why programs get rejected

This is the highest-value logic in the product. <cite index="102-1">Common RAVS failure causes: missing required sections such as no rescue plan in a confined space program, generic templates that never name the company, failing to cite the correct OSHA standards, omitting training frequency, and leaving out documentation forms like inspection checklists or permit templates.</cite> <cite index="100-1">Reviewers look for procedure-level specificity — named responsible parties, inspection frequencies, and step-by-step procedures for the hazardous tasks the crews actually perform; blanket language like "we comply with all applicable OSHA standards" fails on every platform.</cite>

Every program is scored against a shared element set plus program-specific elements.

**Universal elements** (check all programs for these):

```
company_named          company name appears in body text, not a placeholder
purpose_scope          purpose and scope stated
responsible_parties    named roles: program administrator, competent person
citation_correct       correct standard cited for this program
procedures_specific    step-by-step, task-level, matches declared scope of work
training_requirement   training named AND frequency stated (usually annual)
training_records       states that training is documented and retained
inspection_frequency   audit/inspection cadence stated
recordkeeping          what is retained and for how long
forms_attached         referenced checklists/permits actually included
review_cycle           revision date and review interval present
enforcement_link       links to the disciplinary policy
```

**Program-specific required elements** (non-exhaustive, extend per program):

- `confined_space` → permit form, atmospheric testing sequence, attendant duties,
  **rescue plan incl. non-entry retrieval**, rescue service contact and response time
- `respiratory` → medical evaluation, fit testing protocol and frequency, cartridge
  change schedule, facial hair policy, program administrator
- `loto` → equipment-specific procedures, group lockout, shift change, contractor
  coordination, annual periodic inspection by someone other than the authorized employee
- `fall_protection` → anchorage criteria, **suspended-worker rescue plan**, equipment
  inspection cadence, leading edge / controlled access
- `hazcom` → chemical inventory, SDS access method, labeling system, non-routine tasks
- `hot_work` → permit form, fire watch duration after work, gas testing
- `excavation` → competent person named, soil classification, protective system selection
- `electrical_safety` → arc flash boundary, PPE category table, energized work permit
- `sse` → definition of SSE period, mentor ratio, identification method (sticker/hard hat)

**Output:** a per-program element report with `present | weak | missing` and the page
where each element was found — which is also the input to §5.

## 5. The answer key (highest-leverage unbuilt feature)

<cite index="89-1">ISN's submission flow requires the contractor to answer a list of questions per program and enter the page number range where each answer appears — for example "1-2" for a two-page chapter.</cite> Doing this by hand across 25 programs is hours of tedium and is where people give up.

Because the extraction pipeline already has `page_map`, generate this automatically:

```
AnswerKey[program_key] = [
  { question_id, question_text, answer: yes|no, page_range: "12-14",
    confidence, snippet }
]
```

Deliver as an on-screen checklist the user works down while inside ISN, plus a printable
PDF. For programs CertLoop generated, the page ranges are known exactly at render time —
emit them, don't re-derive them.

Ship a first version even if the question set is only approximately right. Nobody else
automates this and it is the thing a user will tell another contractor about.

## 6. Statistics system (Q&A)

<cite index="99-1">The statistics submission covers TRIR, DART and LTIR calculated from OSHA 300 logs, EMR from the official NCCI or state rating bureau document, plus hours worked, fatality count, OSHA inspection and citation history, and annual revenue and employee count.</cite>

```
TRIR = (recordable_incidents × 200,000) / total_hours_worked
DART = (days_away_restricted_transferred_cases × 200,000) / total_hours_worked
LTIR = (lost_time_cases × 200,000) / total_hours_worked
```

Store three years. <cite index="98-1">ISN verifies these against the 300A summaries, and hiring clients set maximum TRIR thresholds commonly in the 1.0–2.0 range — exceeding the threshold drops the grade regardless of how well the rest of the account is completed.</cite>

Build:
- A calculator that derives TRIR/DART/LTIR from an uploaded 300A rather than asking the
  user to type rates they will get wrong.
- A **reconciliation check**: recompute from the 300A and flag mismatch with what the
  user reported. This is a top rejection cause and nobody warns them.
- Threshold comparison per hiring client, with an explicit "we don't know this client's
  threshold" state rather than a guess.

**EMR:** annual letter from the workers' comp carrier — <cite index="100-1">the carrier-issued letter, not a broker summary</cite>. Needs three years, each in its correct year slot; <cite index="101-1">putting EMR letters in the wrong year's drop box is the most common reason they get rejected</cite>. Model `emr_year` as a first-class field and validate the letter's stated policy year against the slot.

## 7. Insurance system

<cite index="102-1">Certificates are needed for general liability, workers' compensation, auto liability, and umbrella/excess, with each hiring client setting minimum coverage; certificates must carry the correct additional insured endorsements, waiver of subrogation language, and limits, and this is one of the most common rejection areas.</cite> <cite index="100-1">GL limits of $1–5M per occurrence are common in oil and gas.</cite>

Parse ACORD 25 into structured coverage lines:

```
Coverage { type: GL|WC|AUTO|UMBRELLA|POLLUTION|PROFESSIONAL,
           carrier, policy_number, eff_date, exp_date,
           each_occurrence, general_aggregate, products_comp_op,
           additional_insured: bool, waiver_of_subrogation: bool,
           primary_noncontributory: bool, notice_of_cancellation_days }
```

Then diff against a `ClientInsuranceRequirement` record per hiring client. Output the
gap as a **sentence the user can forward to their insurance agent** — that email is the
actual deliverable, not a dashboard row.

## 8. Questionnaire (MSQ) system

<cite index="95-1">The questionnaire runs from several hundred to a couple of thousand questions depending on the hiring client's needs.</cite> You will not replicate it, and you should not try.

Do instead:
- Maintain a mapping `msq_question → evidence CertLoop holds`, so the product can
  pre-answer the subset it can support and flag contradictions with uploaded programs.
- Provide a **consistency checker**: user pastes or exports their MSQ answers, product
  flags answers that contradict the documents on file. Inconsistency between
  questionnaire and evidence is a named top-cause of review flags.
- Model the dependency: an MSQ answer change can add RAVS requirements. When the user
  records an MSQ change, regenerate the requirement set and show the diff.

## 9. Training records system

<cite index="91-1">Training documents are distinct from safety programs — they are the attendance rosters or sign-in sheets showing employees were trained on the submitted programs, and ISN requests this evidence at random. One roster per topic is sufficient. A toolbox talk qualifies, but the instructor's name and signature must appear on the sign-in sheet, which is a common omission.</cite>

Build:
- `TrainingRecord { program_key, date, instructor_name, instructor_signature: bool,
  attendees[], source: toolbox_talk|formal|vendor, document_id }`
- A matrix view: programs down, training-evidence status across. Any submitted program
  with no roster is a live exposure — surface it.
- A roster generator: pick a program, pick attendees from the employee list, produce a
  sign-in sheet PDF with the instructor and signature blocks already laid out. Most
  contractors fail this on formatting, not on substance.
- Employee-level records: certs with expiry (OSHA 10/30, confined space, respirator fit
  test, H2S, first aid/CPR, forklift, TWIC, NCCCO, welding quals).

## 10. The clock

Every date in the system feeds one status model. Nothing else in the product should
compute recency independently.

```
overdue → due_soon (≤14d) → upcoming (≤60d) → scheduled → no_date
```

Recurring obligations to model as first-class, not as ad-hoc reminders:

| Obligation | Cadence |
|---|---|
| OSHA 300A posting | Feb 1 – Apr 30 annually |
| OSHA 300A electronic submission | by Mar 2 annually |
| EMR letter refresh | annually, on policy anniversary |
| COI renewal | per policy expiry, alert at 60/30/7 days |
| RAVS revalidation | <cite index="92-1">typically every 2 years</cite> |
| Statistics update | annually after year-end close |
| Training refresh | per program's own stated frequency, usually annual |
| Hiring client deadline | ad hoc, from the client's email |

Reminders fire at 60/30/7 days. Overdue items pin to the top of the dashboard and change
the Overview header.

## 11. Rejection taxonomy

Drives `/rejection`. Classify the pasted reviewer feedback into a known cause, then
route to the specific fix. Seed set:

| code | Cause | Fix path |
|---|---|---|
| `R01` | Generic template, company not named | regenerate with company profile |
| `R02` | Required section missing (e.g. no rescue plan) | element-level patch |
| `R03` | Wrong or absent standard citation | citation correction |
| `R04` | Training frequency not stated | insert frequency clause |
| `R05` | Forms/permits referenced but not attached | attach form pack |
| `R06` | Procedures not specific to declared scope | rewrite procedures section |
| `R07` | Page range answers wrong or missing | regenerate answer key (§5) |
| `R08` | MSQ answer contradicts uploaded program | consistency report |
| `R09` | EMR in wrong year slot | reslot |
| `R10` | EMR is broker summary, not carrier letter | request correct letter |
| `R11` | Reported rates don't reconcile with 300A | recompute and correct |
| `R12` | 300/300A missing for a prior year | backfill guidance |
| `R13` | COI missing additional insured / waiver of subrogation | agent email template |
| `R14` | COI limits below client minimum | agent email template |
| `R15` | Training roster missing instructor signature | regenerate roster |

Each code needs a public explainer page (§12) and an in-product fix action.

## 12. What the website is missing

Content and surface gaps, in rough order of value:

1. **Requirement explorer, public and free.** Trade × platform → the list of programs,
   records, and statistics a file is normally built from. This is simultaneously the
   lead magnet, the demo, and hundreds of indexable pages
   (`/requirements/welding/isnetworld`). Nothing on the site currently answers the
   question that brings people in.
2. **Free calculators.** TRIR, DART, LTIR from hours and incident counts; EMR
   explainer. High-intent, high-volume, trivially buildable, and they capture the
   person mid-panic.
3. **Rejection-reason library.** One page per code in §11 — these are searched verbatim.
4. **Glossary.** RAVS, RAVS 360, MSQ, Q&A, TRIR, DART, LTIR, EMR, SSE, ACORD 25,
   additional insured, waiver of subrogation. Constantly searched, zero on the site.
5. **Cost comparison.** Consultants run $3,000–$8,000/yr; <cite index="47-1">ISN's own subscription starts around $875/year and scales with workforce size</cite>; <cite index="98-1">the normal path from registration to compliant runs 30 days or more</cite>. None of this appears anywhere on certloop.net.
6. **Sample output before upload.** Nobody sends their safety manual to an anonymous
   site on faith. Show a realistic example gap report above every upload control.
7. **A named human with a credential.** No name, no photo, no phone number currently.
   For this buyer that is disqualifying, and it is the cheapest fix on this list.
8. **Platform coverage stated plainly.** Which platforms are supported today vs. not.

## 13. Extraction requirements

The product currently reports unreadable files and stops. Both failures in the test
account are scans, and scans are the norm — this buyer's manual is a photographed
binder.

1. Digital text layer.
2. OCR fallback when no text layer or low confidence.
3. Page-image review flow when OCR confidence stays low: show the failed pages, let the
   user confirm a handful of facts, don't discard the document.
4. Accept `.doc`, `.docx`, `.jpg`, `.png`, and multi-image uploads.
5. Retain a `page_map` (text → page number) on every extraction — §5 depends on it.
6. Classify `doc_type` on ingest and route to the right parser (ACORD 25, 300A, EMR
   letter, program, roster).
7. Deduplicate by content hash; version rather than duplicate.

## 14. Dashboard information architecture

Derived from §1–§11. Replaces the current Overview / Requests / Documents / Programs /
Maintenance / Company / Help structure.

- **Overview** — one completeness figure per hiring client (`n of m items in place`),
  the overdue stack, and one next action. No stat tile that can render empty; three
  tiles maximum, each with an instruction and a link when it has no data.
- **File** — the requirement set as a working checklist, grouped by the six categories
  of §1, filterable by hiring client. This is the product's spine and does not currently
  exist.
- **Documents** — one section, two tabs (uploaded / prepared), versioned, deduped, with
  extraction status and expiry per document. Merge the current Programs page into this.
- **Programs** — becomes a *generator*, reached from the requirement checklist, not a
  parallel nav item listing the same four items.
- **Training** — the program × evidence matrix and the roster generator (§9).
- **Insurance** — parsed coverage lines vs. client requirements, plus the agent email.
- **Statistics** — three-year TRIR/DART/LTIR/EMR grid with the 300A reconciliation check.
- **Calendar** — everything in §10 in one view.
- **Company** — profile that seeds requirement generation; replace the 50-state
  checkbox grid with a searchable multi-select defaulting to the home state.

Two rules for the whole dashboard: no bare `—` anywhere, and any date in the past must
visibly change the page it appears on.

## 15. Constraints

- No payment processor. Paid work ends in a stored quote acceptance, not a checkout.
- No predicted grades, no "guaranteed approval," no claim CertLoop determines
  compliance. Programs are drafts prepared for the contractor's own review and
  submission.
- Keep the not-affiliated disclaimer in the footer and Terms, unchanged.
- Requirement lists, element sets, and rejection codes live in config, not in code.
