# Task 063 — PDF generation was failing in production for everybody

## What happened

Every attempt to generate a program document failed on the deployment:

    ENOENT: no such file or directory,
    open '/ROOT/node_modules/pdfkit/js/data/Helvetica.afm'

It worked locally. It worked in the test suite. It had presumably never
worked in production since 058 shipped.

## Why

`render-pdf.ts` carried a comment saying pdfkit "embeds its own copies of the
base-14 fonts, so nothing here depends on a font file being present in the
deployment". That is not true. Naming Helvetica avoids shipping a *typeface*,
but pdfkit still reads the AFM *metrics* for it off disk at startup, from its
own package directory.

The giveaway was `/ROOT/`, which is not a real path — it is the bundler's
placeholder for the project root. pdfkit was being bundled rather than left as
an external, so the `__dirname` it used to find its font data was rewritten at
build time to a location that exists on no machine.

The plausible-sounding diagnosis was wrong. It looked like a file-tracing
problem, and the fix would have been `outputFileTracingIncludes`. Checking the
build's own `.nft.json` first showed all fourteen `.afm` files, Helvetica among
them, already traced into the programs route. The files were in the deployment
the whole time, under their real path — nothing could find them, because the
code was looking somewhere imaginary.

## The fix

One entry: `pdfkit` added to `serverExternalPackages` in next.config.ts,
joining the three packages already there for exactly this reason. The config's
own comment described the failure mode precisely and pdfkit had simply been
left off the list.

Verified against the build output rather than by reasoning about it. Before:
`/ROOT/node_modules/pdfkit` appears in `chunks/ssr/_189-sde._.js` — the same
chunk named in the production stack trace. After: that string is gone from the
build entirely, pdfkit resolves through an `[externals]` chunk as a real
runtime `require`, and the `.afm` files are still traced.

The misleading comment in `render-pdf.ts` was replaced with what is actually
true, including the instruction not to remove pdfkit from that list.

## The test that could not have caught this

`render-output.test.mts` renders a real PDF and asserts it begins with
`%PDF-`. It passed on every run while this was broken for every customer,
and no improvement to it would have helped: tests run in Node, where
`require("pdfkit")` resolves normally and the font read succeeds. The
deployment ran bundled code. Nothing about the rendering code was wrong.

So the new test asserts the *configuration* instead — that all four packages
that read their own files at runtime are excluded from the bundle. It was
checked by removing pdfkit and confirming it fails. It exists mainly as a note
to whoever next sees a bare array of four package names and no reason for it.

## Worth noting

This class of bug — works locally, works in tests, fails only when deployed —
has now happened once and will happen again with the next library that reaches
for a file inside its own directory. The list in next.config.ts is the place
that knowledge lives.
