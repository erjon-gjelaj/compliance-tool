## Fix — service role grant on the submissions table

The first production submission after task 025 failed with `permission denied
for table submissions`.

Worth recording why that message is ambiguous. It is a *table privilege*
error, not a row level security one — an RLS refusal says "new row violates
row-level security policy" instead. So it means the connecting role has no
rights on the table at all, which can happen two ways: the grant is missing,
or the configured key is not the service-role key. Migration 0002 revokes
everything from `anon`, so a publishable key pasted into
`SUPABASE_SERVICE_ROLE_KEY` produces this exact error.

The code change covers the first cause. Migration 0002 relied on Supabase's
default privileges to grant the service role access to a newly created table.
That normally holds, but it depends on which role created the table, and
leaving it implicit is not worth the ambiguity when the failure looks like a
configuration problem. `grant all on public.submissions to service_role` is
now explicit. The migration is idempotent, so re-running it is the fix.

Also worth stating plainly, since it is the thing that makes this confusing:
service_role bypassing RLS does **not** mean it bypasses grants. They are
separate mechanisms and the table privilege still has to exist.

DEPLOY.md now carries the one-line query that tells the two causes apart.

## Task 026 — document uploads

Scope B deliverable 2. Step 4 of the intake, plus everything that has to be
true before asking someone to hand over their safety file.

**Uploads do not pass through this server, and that is not a preference.**
Vercel caps a serverless request body at 4.5MB. Ten files at up to 10MB each
could never be posted to a server action — the request would be refused
before any of our code ran. So the browser asks for a signed upload URL per
file, sends the bytes straight to Supabase, and then asks us to confirm what
landed. A signed upload URL is a capability for one specific object path: it
cannot write anywhere else, overwrite anything, or read anything.

**The cost of that is validating twice, and the two checks do different
jobs.** Before signing, we check what the browser *claims* — name, declared
type, size. That is cheap, catches honest mistakes before anyone spends
mobile data on them, and is trusted for nothing. After upload, each file is
downloaded back and its leading bytes are sniffed. That is the check that
decides. A file called `program.pdf` declaring `application/pdf` can be
anything; its first four bytes are much harder to argue with. Anything that
isn't what it said it was is deleted from storage rather than recorded.

The .docx case is worth recording because it cannot be solved cleanly: a
.docx *is* a zip, so its magic bytes are identical to a plain archive.
`sniffFileType` accepts `PK\x03\x04` only when the name claims .docx, which
is as far as a magic-byte check can go. Unpacking a stranger's archive to
look for `word/document.xml` is exactly the thing not to do, so it doesn't.

Underneath both sits the bucket itself: private, with its own
`allowed_mime_types` allow-list and `file_size_limit`. That is the floor a
client cannot talk past, and it is what actually keeps executables and
archives out. Private means there is no readable URL for an object at all —
not an obscure one, none. Reads happen through a signed URL with a five
minute expiry, minted server-side.

**Consent is a timestamp, not a boolean**, so the record says when they
agreed rather than merely that they did. It is only asked for when there is
something to consent to: reaching step 4 and sending nothing is a normal,
complete submission.

**Deletion had to be something a person can actually carry out**, not a
function nothing calls, so `deleteSubmission` is reachable through
`DELETE /api/submissions/<id>` behind a shared secret in `ADMIN_SECRET` —
the same mechanism the internal page will use in task 031. With the secret
unset the route answers 404 rather than 401, so an unconfigured deployment
doesn't advertise that it exists. Two details in the implementation are
deliberate. Storage is emptied first and the row deleted second, so a
failure halfway leaves a record pointing at files that are already gone —
visible and recoverable — rather than files nothing points at. And the file
list comes from the bucket as well as from the table, so a file whose insert
failed still gets removed; that is precisely the file you cannot afford to
keep.

**Other decisions worth knowing.** Storage paths are built from the
submission id, an index and a fresh uuid, never from the uploaded file name —
that name is recorded for display and is otherwise treated as hostile input.
A confirmation path is checked to start with its own submission id before
anything is read, so naming someone else's path gets you nothing. If an
upload fails partway the step stops rather than pressing on, because sending
a partial set under a success panel would tell someone their documents were
received when some were not. Rejected files are surfaced rather than
swallowed, for the same reason: silence about a document nobody looked at is
the wrong answer.

**Also in this change.** A `/privacy` page written for the person about to
upload rather than for a lawyer, linked from the upload step where it is
relevant and from the footer; it is deliberately not in the header, which
stays a flat row of three. `LEGAL_LINKS` keeps it out of the header while
still feeding the footer and the sitemap. Both intake emails now list
attached documents by name rather than counting them, since "3 files
attached" is not something you can check against what you sent. The FAQ
answer on what is stored now covers uploads.

**Manual steps**, added to DEPLOY.md: run migration 0003 (it creates the
private bucket from SQL, so there is nothing to click, but check it shows as
Private), and set `ADMIN_SECRET` locally and in Vercel — without it a
deletion request cannot be honoured.

Not tested: no `.env.local` here, so nothing was uploaded from this machine.
Build and lint pass clean.

## Task 027 — analysis pipeline

Scope B deliverable 3. Extract text, ask the model, validate the answer, send
an email — and never leave anyone hearing nothing.

**Extraction is libraries, not a model, and that was the explicit call.**
`unpdf` for PDFs (a serverless build of Mozilla's pdf.js — no native binary,
which is what rules most PDF tooling out on Vercel), `mammoth` for .docx,
`word-extractor` for legacy .doc. All free, all permissive, all local. The
reasoning is in the module docstring: extraction is a mechanical job with a
right answer, and a language model does it slower, non-deterministically, at
a cost per page, and with the ability to invent text that isn't in the file —
which is the one failure this project can least afford.

**OCR is a capped fallback, and it is honest about what it is.**
`tesseract.js` runs only when normal extraction yields nothing and the file is
an image: three images per submission, 6MB each, language data cached in
`/tmp` so the ~15MB download happens once per cold start rather than once per
file. Its output is marked `ocr` rather than `ok`, and the prompt is told what
that means — a phone photo taken at an angle produces confident nonsense, so
that text is an indication to confirm and never proof. HEIC has no decoder
here at all and says so rather than failing obscurely.

**The distinction the whole thing rests on** is that "unreadable" is not
"empty". A scan with no text layer and a document containing nothing extract
identically, and collapsing them into one null is exactly how silence starts
implying "reviewed and fine". `text_status` keeps them apart, the email lists
unreadable files by name, and the extractor is the authority on that list
rather than the model — a file we could not read is a fact, not a judgement.

**Structured output, twice.** The schema is sent to the API as a
structured-output format, so generation is constrained rather than only
checked afterwards; it is then validated on the way back anyway, because
constrained decoding is not something to take on trust for text that gets
emailed to a stranger. The validator also enforces what a schema cannot:
every item must carry a basis, an `unknown` cannot be high confidence, a
hiring-client requirement must be `unknown`, and a citation is rejected unless
it sits on an OSHA item and has been confirmed to support the claim. Any of
those fails the whole analysis.

**Every failure path sends the same honest explainer** — no API key, a model
error, a refusal, malformed JSON, a rule violation. It says plainly that the
automated review did not produce something safe to send and that a person will
look instead. Refusing to send is always available; unsaying a confident wrong
answer is not. The internal copy of that email is subject-lined NEEDS A HUMAN,
because that is what it means.

**It runs after the response, not inside it.** Reading several PDFs, running
OCR and making a model call takes far longer than anyone holds a form open
for. `after()` from next/server keeps the invocation alive past the flush, so
the person who tapped send gets their success panel immediately and the review
arrives when it is ready.

**Everything is logged.** The `analyses` table records the system prompt, the
user prompt, the raw output, the validated result, the error, the token counts
and the duration — written before the email is sent, so an output that breaks
the sender is still on record. This is the only way to find out whether the
guardrails hold. Read the first thirty closely.

**Two things deliberately left thin.** `lib/requirements/` is a near-empty
placeholder with a TODO-VERIFY that tells the model it has no verified basis
for asserting any requirement; the typed versioned version is task 030 and
needs real domain research first. And the email is plain text — task 028
renders it properly. Both are honest intermediate states rather than
placeholders pretending to be finished.

Also: `word-extractor` ships no types, so there is a hand-written declaration
in src/types covering only the two calls actually used — a declaration that
claims more than it has been checked against is worse than a small one,
because the compiler believes it. The four extraction libraries are in
`serverExternalPackages`; they resolve their own assets at runtime and
bundling rewrites those paths into failures that only appear in production.

Not tested: no `.env.local` and no API key in this working tree, so no
document has been extracted and no model call made from here. Build and lint
pass clean.

## Task 027, revised — the model is gone

The human's call, and it changes the shape of the product rather than just
swapping a library: no LLM anywhere in this project.

**What was removed.** `src/lib/anthropic.ts`, `src/lib/analysis/prompt.ts`,
the `@anthropic-ai/sdk` dependency, `ANTHROPIC_API_KEY` and `ANTHROPIC_MODEL`
from the example env and DEPLOY.md, and the model, prompt, raw-output and
token columns from the `analyses` table. `CLAUDE.md` and `business-model.md`
said the pipeline calls the Anthropic API; both now say the opposite, and
CLAUDE.md has a short "No language models" section so the next person does
not reintroduce one by accident.

**What replaced it.** `src/lib/analysis/match.ts` builds the review by
searching the extracted text. The rule it follows is that everything reported
has to be a fact about a file or about an answer the contractor gave us. "We
searched the four documents you sent for the words a lockout/tagout programme
is written in, and did not find them" is checkable, reproducible, and true
whether or not anyone has researched what ISNetworld asks for. "You need a
lockout/tagout programme" is a different kind of claim and this code is not
in a position to make it.

That turns out to fit the regulatory rules better than the model did. Same
submission, same answer, every time. Every finding names the file and the
phrase. Nothing can be invented, so the guardrails are structural rather than
instructions someone hopes are followed.

**`lib/requirements/` stopped being a placeholder**, because the matcher
needs it. Twelve entries, each with the phrases that identify that document
inside an upload, written to be edited by someone who is not a developer —
the field list and the editing instructions are at the top of the file. Every
entry is `verified: false` and the output says so out loud: an unverified
requirement is reported as something commonly asked for, never as something
this contractor must have. Nothing carries an OSHA source, and nothing may
until a real citation has been retrieved.

**Matching is on word boundaries**, so "loto" does not fire inside "photo".
It is still a text search and it can be fooled — a contents page listing
sections the document never contains will match — which is why the basis
names the phrase and the file rather than just asserting the finding.

**Two bugs found by actually running it.** The price band came back "low"
when nothing had been read at all, because a ticked checkbox counted as an
established item; "low" there reads as "this is a small job" when the honest
answer is that we have no idea, so it is now "unknown" whenever no document
was readable. And the summary's "N of M look covered" counted the
hiring-client item in its denominator — an item that is permanently unknown
by design, so it dragged every ratio down and invited the reader to think a
category had been missed.

**Both layers were exercised for real** against fixtures, which is the first
time any of this code has run. A hand-built PDF with a text layer extracts
correctly; the same PDF with the text operators blanked comes back
`unreadable` rather than empty, which is the distinction the whole design
rests on; mammoth's own test .docx extracts; an empty .docx is `unreadable`;
an unknown MIME type is `unsupported`. Then four matcher scenarios — no
documents, a readable manual, an unreadable scan, an OCR photo — all pass
their own schema validation, and the OCR path correctly reports one
confidence level down. The harness was scratch and is not committed.

**Still true from the earlier version.** Extraction is `unpdf`, `mammoth` and
`word-extractor`, with capped `tesseract.js` OCR as a fallback for images.
Every failure path sends the same honest explainer. The run is logged before
the email goes out. It runs via `after()` so the form returns immediately.

Build and lint pass clean.

## Fix: "not sure" was hiding every missing document

The first live test with a real file turned up a bug the empty submission
could not have shown. A readable PDF came back with five items present and
seven "we couldn't establish", when those seven were genuinely absent from
the document and should have read "looks missing".

`documents_unsure` was checked before the search result in `itemFor`, so
ticking "not sure what my file contains" on the form short-circuited every
unmatched requirement to `unknown` and made the `likely_missing` branch
unreachable. The email contradicted itself as a result: the header said it
had read and searched the file, then every missing item gave a form answer
as its basis.

This mattered more than it looked. The whole point of the product is telling
someone what they are missing, and the person who ticks "not sure what my
file contains" is exactly the contractor described in business-model.md. That
user could have uploaded a complete file and never been told a single thing
was absent.

The form answer now only applies when there is nothing to search. Once a file
has actually been read, the search outcome is the better evidence — "not sure
what my file contains" describes what they know, not what the document says.

Verified against the real submission shape: 5 present / 8 unknown / 0 missing
before, 5 present / 7 missing / 1 unknown after, the remaining unknown being
the hiring-client item that is permanently unknown by design. Checked three
regressions too — unsure with no files, not-unsure with no files, and unsure
with an unreadable file all still return unknown. That last one is the one
that matters: a non-match on a file we could not read must never become a
finding.

Also fixed the question template, which dropped a noun-phrase label into
"Confirm whether X applies to you" and did not agree in number - "Confirm
whether Training records for the crew applies to you", and worse, "Confirm
whether Whatever Plant specifically requires applies to you". The label now
leads the line.

Build and lint pass clean.

## Task 028 - the review email gets an HTML half

Everything 028 actually specified was already working and confirmed in
production by a real submission: preliminary header, items grouped by
confidence with low-confidence rendered as questions, unreadable files
listed, one CTA, non-binding price band. What was left was purely
presentation.

Considered pointing a design tool at this and decided against it. HTML email
is not the web: Outlook lays out through Word's engine, so flexbox, grid,
custom properties, external fonts and even a <style> block are unreliable or
simply ignored. Anything generated as a modern web page would have needed
rewriting line by line. So the email is presentation tables and inline
styles throughout - tedious to write, and the only thing that renders the
same in Outlook, Gmail and Apple Mail.

It uses the site palette by hex since named variables do not exist here, and
rebuilds the tape-rule signature detail out of bordered table cells, because
no mail client can be trusted to render the SVG the site uses. Status pills
carry the finding: calm green for present, rust for missing, grey for
unknown.

Everything interpolated is escaped. File names and the hiring client's name
come straight off a public form, and the client's name is interpolated into
a requirement label - an ampersand in a company name would break the markup
with no ill intent at all. Tested with "Plant & Co" for exactly that reason.

text/plain remains the source of truth for what the review says; this module
only decides how it looks, and both parts go out on every send, so a client
that refuses HTML still gets the whole review.

**Two content fixes went in alongside.** The empty-submission case no longer
prints thirteen expanded entries that all say the same thing - that read as
though the tool had done nothing, and it is a common case rather than an
edge one, since "not sure what my file contains" is exactly the contractor
this is built for. It now leads with the questions, which are the only
actionable part, and collapses the catalogue to a list of names. And the
price heading says "About pricing" rather than "What this would cost" when
the band is unknown, instead of promising a number and then not giving one.

Reordering the questions immediately exposed a copy bug: two of them said
"the categories above", which is wrong the moment the questions lead. Both
are position-neutral now.

Rendered both states to files and looked at them in a browser rather than
assuming the markup was right. Build and lint pass clean.

**Open risk:** none of this has been seen in a real mail client. Browser
rendering is a weak proxy for Outlook in particular. Sending one to a real
inbox is the check that matters.

**Logo decision: no image, mark rebuilt from borders.** Asked whether to put
the logo in the email. Decided against an image of any kind. Remote images
are blocked by default in Outlook desktop and for many Gmail users, so the
single branded element would show as a grey placeholder for a good share of
recipients - worse than not having it at all. They are also the mechanism
tracking pixels use, and certloop.net is a new domain with no sending
reputation posting automated mail to contractors sitting behind corporate
filters, so deliverability is worth more than a logo. A CID attachment would
dodge the blocking but puts a paperclip on an email with nothing attached.

The mark is only a baseline with two long ticks and two short ones, so
borders reproduce it exactly. It is now in the masthead next to the wordmark,
built from table cells, no image involved, rendering unconditionally
everywhere.

## Two fixes off the first real HTML email

Erjon put a submission through and got the designed review. Two things came
back, both fair.

**The mark was too thin and did not match.** It had been built by eye rather
than from the SVG. Reading components/wordmark.tsx properly: on a 24 grid at
stroke-width 2, ticks sit at x=3/9/15/21, so they are 2 wide with 4 between,
the baseline runs x=2..22 for exactly 20 across, long ticks are 9 and short
ones 5. The email version had 5px gaps instead of 4 and a 23px baseline
instead of 20, so the proportions were wrong. Rebuilt from those numbers and
scaled 1.5x, which keeps every ratio and stops it reading as wispy next to
19px bold text - at true size the 2px baseline nearly disappeared. It looked
right on the Gmail phone app already; this is for the desktop view.

**The confirmation email was still plain text.** Only the review and the
explainer had been given an HTML half. The confirmation now has one too, with
what they sent us as a two-column table rather than aligned monospace, which
does not survive proportional fonts. It carries no preliminary-review
disclaimer, deliberately - it is not a review and must not look like one,
and there is nothing yet to disclaim.

That meant the masthead kicker could no longer be hardcoded to "Preliminary
gap review", so it is a parameter now and the confirmation and explainer both
read "Gap check received". The document title was leaking the same string and
is fixed with it.

The internal copies stay plain text on purpose. They are read by one person
scanning for what came in, and monospace alignment is better for that than
styling.

Build and lint pass clean.

**The mark again - it was a table bug, not a size preference.** All four ticks
were rendering the same length, which is why it did not read as the logo: the
long/short alternation is the whole character of a tape rule. Cause: a td's
height is a minimum, and every cell in a row stretches to the tallest cell in
that row. The colour was on the cell, so the two short ticks were stretched to
match the long ones and painted full height. The colour now sits on a
fixed-height div inside each cell, so the cell can stretch while the mark does
not. Also doubled rather than 1.5x, since it still read thin. Measured on the
rendered page: baseline 40x4, ticks 18/10/10/18, which are the SVG's ratios.
Verified by measurement rather than by eye - the browser pane would not
composite a screenshot on this pass.

**Widened the email to 680.** The 600px convention comes from preview panes
much narrower than anything in use now, and in a maximised window it read as
a thin ribbon. Still comfortably inside what Outlook and Gmail render, and
max-width keeps it fluid on a phone.

analysis logging in 027. The missing piece was the internal page.

/internal/submissions is now behind ADMIN_SECRET. The secret is posted once
and exchanged for an httpOnly cookie rather than carried in a URL - a ?key=
would end up in browser history, in the Referer header of any outbound link,
and in Vercel's request logs. The cookie stores a sha256 of the secret rather
than the secret, so a stolen cookie jar does not also hand over the value
guarding the delete endpoint. Comparison is constant-time. An unset
ADMIN_SECRET locks the page rather than opening it.

The page is read-only. Deletion stays behind the DELETE endpoint and a curl
command rather than becoming a button on a page reachable with one shared
secret - a stray click should not be able to destroy a customer's uploads.
Partial rows are listed alongside complete ones, because someone who dropped
out at step two says more about the form than a completed intake does.
