## Task 006 — Nav, smooth scroll, footer

The nav is a flat row of About / FAQ / Contact that stays visible at every
width. No hamburger, no dropdowns — three short labels fit on a 375px phone
with room left, and hiding four links behind a button would be ceremony for
its own sake. "Free gap check" is gone from the nav as instructed; it survives
as a footer link, since from `/about` there still needs to be a route back to
the form.

The link list now lives in `src/lib/nav.ts` and is read by the header, the
footer, and the sitemap. Adding a page is one line in one file rather than
three edits that drift.

Header and footer moved out of `page.tsx` and into the root layout. Otherwise
every new page would have had to remember to include them, which is exactly
the kind of thing that gets forgotten on page five.

Smooth scroll is CSS `scroll-behavior` on `html`, not JavaScript, wrapped in
`prefers-reduced-motion: no-preference`. It costs nothing, works on a plain
anchor, and anyone who has told their OS they want less motion still gets the
instant jump.

The footer now carries the wordmark, the ISN/Avetta disclaimer, a page list, a
contact block, a tick rule, and a copyright line.

**One thing worth knowing:** the copyright year is baked at build time, because
every page here is static. It advances on the next deploy, not at midnight on
1 January. The alternative is reading the clock in the browser, which costs a
hydration mismatch and a client bundle for one number. For a site that
redeploys on push this is the right trade, but it does mean a site left
undeployed for a year will show a stale year.

### Collapsible FAQ

Eleven native `<details>`/`<summary>` disclosures replacing the flat list. No
JavaScript, keyboard support for free, all collapsed by default.

The thing I checked carefully: the answers stay in the DOM whether open or
closed — 490 characters present in the server HTML of a collapsed answer. That
matters because this page is meant to be indexable, and a JS accordion that
mounts answers on open would have hidden the substance from crawlers. The
FAQPage JSON-LD still matches what's rendered. Questions also became `h3`
inside the summary, which is a better heading hierarchy than the `dt` they
replaced.

**The open/closed indicator took three attempts, and the reason is worth
knowing.** First, Tailwind's `group-open:rotate-180` — the class sat in the
markup and generated no CSS whatsoever, so it silently did nothing. Second, an
explicit `details[open] > summary .faq-chevron { transform: rotate(180deg) }`
rule, which compiled correctly into the bundle and matched the element, and
still didn't rotate.

The browser explained it: a transform on a descendant of `<summary>` resolves
to an identity matrix. I proved it by cloning the identical element outside
the `<summary>` — where it rotated correctly — while the one inside stayed at
identity even with `!important` inline. A control span with an inline
`rotate(45deg)` reported its matrix correctly, so the measurement was sound and
the element genuinely wasn't rotating.

The version that ships swaps two icons with `display` instead of rotating one,
which sidesteps the quirk entirely. Verified against a production build:
correct icon in each state, expands and collapses, exactly one icon visible at
a time.

Worth remembering generally — a CSS rule being present and correct in the
built stylesheet, and matching the element, still isn't evidence it renders.

### Switched the mailer to nodemailer over SMTP

Replaced the Resend implementation with nodemailer talking plain SMTP, so it
uses whatever provider already hosts `info@certloop.net` — no third-party
sending service, no extra account, no API key to manage. `src/lib/notify.ts`
is the only file that changed; `actions.ts` calls the same function.

Configuration is `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, plus
optional `LEAD_NOTIFY_FROM` (defaults to `SMTP_USER`) and `LEAD_NOTIFY_TO`
(defaults to `CONTACT_EMAIL`). The keys are documented in
`.env.local.example` and blank ones are already appended to `.env.local`, so
setting it up locally is filling in values rather than remembering names.

**On "create the credentials":** I created the credential *entries* — the
variable names, the file scaffolding, and the documentation. I did not invent
values. The password belongs to the mailbox at your provider and has to come
from you; anything I generated would just be a wrong string. Two things worth
doing when you fill them in: use an app-specific password if your provider
issues them, since it can be revoked without touching the password you log in
with, and set the same variables in Vercel or production will keep logging
that mail is skipped.

Three properties I built in deliberately:

- **A mail failure can never fail a submission.** Verified by pointing a full
  config at a dead port — the error goes to the server log and the submission
  is untouched.
- **Config is all-or-nothing.** A half-filled config is treated as absent
  rather than attempted, so a missing password can't turn into an auth failure
  on every single submission.
- **TLS is mandatory.** Port 465 is implicit TLS; every other port must
  upgrade via STARTTLS before authenticating, so the password never crosses a
  plaintext session. `secure: false` on 587 means "STARTTLS", not
  "unencrypted", which is an easy thing to misread in nodemailer config.

Tested four paths — nothing configured, partial config, invalid port, and
fully configured against an unreachable server. All four return cleanly, and
each now logs exactly one accurate reason. An earlier version logged both the
specific error and the generic "not configured" warning for a bad port, which
would have sent someone looking for unset variables that were in fact set.

**Actual delivery is still unverified.** There are no working credentials
here, so what's proven is config handling, TLS selection and failure
behaviour — not that your provider accepts the message. First submission after
you set the variables is the real test. I also didn't submit the local form to
test, because `.env.local` points at production Supabase and it would have put
a junk row in your live table.

  contractor, so replying answers them.
- **To the contractor** — a receipt, reply-to set to `info@certloop.net`, so
  replying reaches you.

The confirmation copy promises only what the site already promises: a person
reads it, it isn't instant, one email comes back, no mailing list, no call to
book. It repeats their four answers so they have a record, and it carries the
ISN/Avetta disclaimer — this is the one piece of the product that arrives away
from the site, where the footer's context isn't visible, so the "not affiliated,
not a compliance determination" line travels with it.

The two sends are settled independently rather than awaited in sequence. That
matters: a confirmation bouncing on a mistyped address must not also cost us
the internal copy, which is the one email proving the lead exists at all.

**How I verified it.** The real risk here is swapping the recipients — sending
our internal copy to the contractor. Rather than trust a reading of four lines,

message builders are exported so that check is repeatable.

Also re-confirmed against an unreachable server that both sends are attempted,
both failures are logged separately, and nothing throws.

I did not send a live test email. The credentials are in Vercel rather than
here, and sending real mail wasn't something to do unprompted — your next real

### Header and footer chrome, sticky nav, and FAQ accordion behaviour

Five small things you asked for after looking at the live site.

**The phone line disclaimer is gone.** "Email only — we don't run a phone line
yet" read as an apology for something nobody had asked about. The contact
address stands on its own in the footer now. The contact page keeps its own,
longer version ("no phone line and no office to visit yet — when that changes
it will be listed here"), because there it's answering a question the reader
has actually arrived with rather than volunteering a limitation.

**Header and footer now sit on their own surface.** They were previously
separated from the page by a single hairline, which meant the chrome and the
content read as one continuous field. Both bands are now solid millscale —
the near-black already in the palette — so the page's content is bounded by an
actual change of surface.

This is the same colour top and bottom on purpose: it bookends the page rather
than adding two new tones. The light content area is unchanged, so this isn't
the dark-page-with-an-accent look the visual identity rules out.

Three things had to change to make text work on it, and they live together in
a `.surface-dark` class in `globals.css` rather than being sprinkled across two
components:

- **A lifted accent.** Verdigris at full strength measures about 2.5:1 against
  millscale — fine as a mark, not enough for link text. Added
  `--color-verdigris-pale` (`#7fc9b5`), the same copper green raised, which
  lands around 8.6:1. It is used only on the dark bands; the accent on the
  light page is untouched.
- **A readable label colour.** `.tag` is slate-wash, which disappears on
  millscale. Overridden within the dark surface.
- **A visible focus ring.** The verdigris outline is nearly invisible against
  a near-black background, so it switches to the pale step too.

`Wordmark` gained a `tone="invert"` prop for the same reason — its tick mark is
hardcoded to verdigris, which needed the lifted colour on both bands.

**The navbar is sticky.** `sticky top-0 z-50`, no JavaScript. The one real
consequence is that in-page anchors would land underneath it, so `html` carries
a matching `scroll-padding-top: 5.5rem`. Verified: after a jump to
`#gap-check`, the target sits 47px clear of the 73px header rather than behind
it.

**The FAQ opens one item at a time.** Done with the native `name` attribute on
`<details>`, so the exclusive-accordion behaviour is the browser's and this
stays a zero-JavaScript page — the whole point of task 017. Clicking a second
question closes the first; clicking the open one still closes it.

Worth knowing: `name` on `<details>` needs Chrome 120, Safari 17.2 or
Firefox 130. Older browsers ignore the attribute and get the previous
behaviour — several open at once — which is a graceful degradation rather than
a break, and is why this was preferable to adding a client component.

**FAQ questions are no longer selectable.** `select-none` on the `<summary>`.
Dragging across a question to click it used to highlight the text, which looks
like a broken button. The answers stay selectable — that's the part anyone
would actually want to copy.

**Verified in the browser**, not just built: header computes as sticky at the
top on scroll with the dark background, exactly one chevron visible per FAQ
item in each state, setting a second item open closes the first, the summary
computes `user-select: none` while the answer paragraphs compute `auto`, and
no "phone line" text remains in the rendered page. `npm run build` and
`npm run lint` pass clean, all ten routes still prerender static, and the
console is clear.

### A real 404 page

Unmatched URLs were falling through to the framework's default not-found
page. That page ships its own styles and follows the visitor's dark-mode
setting, so a mistyped address on a site that is deliberately light-only
landed on a black screen with none of the site's chrome and no way back into
it.

`src/app/not-found.tsx` replaces it. The root not-found file catches every
unmatched URL for the whole site, not only an explicit `notFound()` call, and
it renders inside the root layout — so it carries the same header, footer,
palette and type as every other page.

The copy assumes the likely reader: someone who followed a stale link or
mistyped an address, plausibly while working to a deadline. So it says plainly
that nothing already submitted is affected, which is the actual worry if you
came back to check on a gap check you sent, and then points at the gap check
and the three interior pages with one line each on what they cover. The
per-page lines are keyed off `NAV_LINKS` rather than retyped, so adding a page
to the nav without a description is a TypeScript error rather than a silent
gap.

**One limitation worth recording.** Next only supports a `metadata` export on
the experimental `global-not-found` convention, not on `not-found.tsx`, so the
browser tab title on a 404 falls back to the layout default — the home page
title. Switching to `global-not-found` would fix the title but bypasses the
root layout entirely, meaning styles and fonts get re-imported by hand and the
page loses the shared header and footer, which is the whole reason this looks
like the site. Not a trade worth making for a tab title, so it stays as is.

`<meta name="robots" content="noindex">` is injected automatically for 404
responses, so nothing extra was needed for SEO.

**Verified in the browser**: an unmatched URL returns a real 404 status,
renders exactly one `h1`, carries the site header and footer, computes the
light galvanise background rather than the default page's dark one, emits the
noindex tag, and every link on it points somewhere real. Build and lint pass
clean.

### A contact form, so the contact page isn't email-only

The "for anything else" section handed you a mailto link and a list of four
things worth including. That works if you use a desktop mail client and
nothing else is in your way; it is a dead end on a phone with webmail, and it
asks someone who is already stuck to open another app and start from a blank
message.

There is now a form on the contact page — name, email, message — that sends
to `info@certloop.net`. The email address is still there underneath it, for
anyone who would rather use their own client or needs to attach something,
since the form deliberately takes no attachments.

**The four things to include stayed.** They now sit above the form as
guidance rather than below a mailto link, which is where someone about to
write the message will actually read them. They are not separate fields: this
is the "anything else" channel, and forcing a complaint or a scheduling
question through four gap-check fields would be the wrong shape.

**The intro copy had to change.** It previously said "no contact form that
disappears into a queue", which would have been an odd thing to keep saying
directly above a contact form. It now says two forms and one email address,
all landing in the same inbox and read by the same person — which is true,
and keeps the point the old line was making.

**No database behind it, and that decision drives the rest.** A gap check
goes into Supabase before any mail is sent, so a bounced email costs a
notification rather than the lead. A contact message has no such record —
email is the only copy. So, unlike the gap-check action, this one refuses to
report success unless the send actually succeeded. If SMTP is down or
unconfigured, the form says the message was not sent and hands over the email
address instead. A success panel over a message that never left would be
worse than an error: the person stops waiting for a reply they were owed, and
we never learn they wrote.

Storing messages in Supabase was the alternative. It needs a second table and
a migration a human has to run in the SQL editor, and it would have meant
this task ending blocked on you the way task 003 did. The email-only version
is complete today and can gain a table later without changing what the page
does.

**No auto-reply to the sender**, which is a departure from the gap-check
flow's confirmation email. The form is public and mailing an address a
stranger typed is the spam-amplification vector already written up in
DEPLOY.md. That is a fair trade for the gap check, which is the actual
product and where the receipt doubles as the person's record. It is not a
fair trade for a contact form whose entire job is to reach our inbox.

**Spam.** A hidden honeypot field, positioned off-canvas rather than
`display:none` because some bots skip fields they can tell are hidden. It is
`aria-hidden`, out of the tab order, and has autocomplete off so a password
manager cannot fill it in for a real visitor. Anything arriving with it
completed is discarded and shown an ordinary success panel, so whatever is on
the other end has nothing to tune against. This is not rate limiting and does
not replace it.

**A real bug found while verifying.** The textarea started as `id="message"`,
and the section it sits in already had `id="message"` on its `<h2>` as an
anchor target. Duplicate ids, and the `<label for="message">` resolved to the
heading rather than the textarea — so clicking the label did nothing and a
screen reader would have announced the field unlabelled. All three fields are
now prefixed (`contact-name`, `contact-email`, `contact-message`) and the
error ids with them; the `name` attributes the action reads are unchanged.
Confirmed afterwards that the page has no duplicate ids at all and every
label resolves to its own control.

**How I verified it.** Composed the outgoing email through a nodemailer
`jsonTransport`, which builds the real MIME message without opening a
connection, and read the envelope back: `to` is `info@certloop.net`, reply-to
is the sender, and `from` stays our own address — putting the sender in
`from` would be forging mail as this domain, which is what SPF and DMARC
exist to reject.

In the browser, against the dev server with no SMTP credentials present: a
valid submission returns the honest failure with the mailto fallback and
echoes back everything typed; an invalid one is caught server-side with the
browser's own checks disabled, showing per-field errors whose ids match the
`aria-describedby` on each field; and a submission with the honeypot filled
is logged as discarded, shows the normal success panel, and — confirmed in
the server log — never attempts a send.

No live email was sent. The SMTP credentials live in Vercel rather than here,
so the first real submission after deploy is the actual proof of delivery.
