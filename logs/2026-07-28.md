# Task 055 — request state, derived from events

## The bug

A request read "Waiting on us" after we had already replied.

`service_requests.status` was a column with three values, set by hand. Replies
were sent from a mail client, outside the product, so nothing ever updated it.
Widening that column to seven values would have produced the same bug with more
words: the fault is that state was STORED rather than DERIVED, and any stored
label is a claim about the world that goes stale the moment somebody acts
outside the app.

## The fix

`request_events`, append-only, and `deriveStatus()` computing the state from
it. There is no `setStatus` anywhere in this product now — to change what a
request says, you record what happened. A derived state can only be wrong if an
event is missing, and a missing event is a visible bug rather than a silent
lie.

Seven states, four visual tones. Two states that mean the same thing to
somebody scanning a list should not be told apart by colour, and only
"needs something from you" draws the eye, because it is the only one that is
their move.

## The judgement that cannot be derived

Whether a reply from us needs something back. "Here's your draft, nothing
needed" and "we can't start until you send the EMR" are both replies from
CertLoop and they leave the request in opposite states — no amount of reading
the prose settles it. So `awaits_reply` is asked of whoever writes the reply.
It is the one thing in the model a human decides, and forcing that choice at
the moment of writing is more honest than inferring it later.

## What actually made this work

The state model would derive "we replied" perfectly and still say "with
CertLoop" forever, because replying happened in a mail client. So:

- `/dashboard/requests` and `/dashboard/requests/[id]` — the conversation, with
  a reply box. A customer message puts it back on us by derivation; replying
  and "changing the status" are the same act and cannot come apart.
- `/internal/requests` — the operator console. Reply, mark in review, draft
  ready, completed, closed. This page writes, where the submissions list
  deliberately does not: a stray click there destroys uploads, here it appends
  to an append-only visible log, and a wrong event is corrected by recording
  the right one.
- Emails both directions, with the message body included rather than a "you
  have a message" nudge. Only a message is mailed — an email per state change
  trains people to ignore the ones that matter. No magic link is minted into a
  reply notification: that would make every reply a credential.

## The backfill decision

Existing requests get a `submitted` event only. Deliberately NOT a reply event
for rows whose old status was `in_progress` — that column is exactly the
unreliable thing being replaced, and seeding the new log from it would carry
the same bad data forward wearing a better shape.

So a request that was genuinely replied to over email will read as waiting on
us until somebody records the reply. That is a visible, fixable wrong, and the
honest starting point.

## Verified

11 new tests on the derivation, 82 lib and 12 UI passing, build and lint clean.
The negative ones: completed is not recomputed from an older unanswered
question, a draft stops being "here is your draft" once someone speaks after
it, and the answer does not depend on the order rows come back in.

Needs migration 0008 run, and a look on production.

# Task 056 — the dashboard becomes an application

Persistent navigation beside the content on a wide screen, above it on a
narrow one. On a phone it is a scrolling row rather than a hamburger: this
audience is on a job site, and a menu that must be opened to find out what is
in it costs a tap on every navigation. There are few enough sections to fit.

Sections: Overview, Requests, Documents, Company, Ask for help. The document
library moved out of the overview into its own section, and requests got one.

The overview is now four figures, one next action, and short lists — no
promotional copy. The two request figures are derived from the event log, which
matters most here: a count on an overview is exactly where a stale status does
the most damage, because nobody clicks through to check it.

Tiles sit on `paper` against the `galvanise` body with a full border. Only the
one representing work waiting on the customer takes the warning treatment, so
the single tile that draws the eye is the only one that is their move. A figure
with nothing behind it renders as a dash rather than a zero — "0 documents"
reads as a measurement, "—" reads as nothing here yet.

Status colour lives in one component now (`status-chip.tsx`), four tones across
six states, so the same meaning cannot look different on two screens.

## Not verified

The signed-in pages cannot render locally — no Supabase credentials — so the
layout, the mobile nav row and the tiles have only been type-checked and built,
never seen. Needs a look on production at both widths.

# Task 057 — pricing as configuration

`src/lib/pricing.ts` holds every number. Nothing outside it hardcodes an
amount, because these are preliminary assumptions that will move once real
review times, revision volume and support burden are known — and a number
written into copy in four places does not move.

Everything is a RANGE under an early-access label. A single figure reads as a
quote, and these are not quotes. `PRICING_NOTE` travels with the numbers
wherever they appear, and says the actual figure is confirmed before work
starts — which is the part that makes a range honest rather than evasive.

One-time services and a maintenance plan both, deliberately. A contractor with
one urgent rejection is not a subscriber, and making them take a monthly plan
to solve a problem they will not have again for six months would lose the sale
and deserve to.

Public `/pricing` page, added to the nav. The 404 page's typed description map
caught the missing entry at build time, which is what that type was for.

The ranges also appear in the help form, next to the ask rather than only on
the pricing page: someone deciding whether to send a request wants to know
roughly what they are in for, and making them open another tab is how a
request gets abandoned. Both read from the same module so they cannot drift.

## One thing I got wrong and fixed

The first draft of the page ended with "CertLoop is not going to take a card
number through a form that was built last week." That is precisely the
defensive self-narration task 046 removed from the rest of the site, written
back in by me. Replaced with what is actually true: card payment is coming, and
until then work already agreed is invoiced directly.

## Verified

Build, lint and 94 tests clean. Page read end to end in the browser.

# Fix — the program form crashed in production

`/dashboard/programs/hazard_communication` returned a 500 on every load.

The page passed the whole `ProgramTemplate` to `ProgramForm`, a client
component. A template carries functions — `showWhen`, `build`, `matchesLabel`
— and functions cannot be serialised across the server/client boundary.

The comment I had written in `registry.ts` asserted the opposite: "Client-safe.
The templates are data and pure functions." That conflated two different
things. A client component may *import* the registry, because the import is
bundled; it may not *receive* a template as a prop, because that is
serialisation. The comment is corrected rather than deleted, since the wrong
version of it is an easy mistake to repeat.

Fix: the page passes `programId`, and the form looks the template up on the far
side. That preserves the property that mattered — the branching the customer
sees comes from the same definition the server validates against — while
staying on the correct side of the boundary.

Checked every other client component's props at the same time: company-form,
request-thread, document-download, help-form and the rest all take strings,
arrays of strings, or plain rows. This was the only one.

## Why nothing caught it

Build, lint and 117 tests all passed. Next normally surfaces this at build
time, but the page is `force-dynamic` and behind a session, so it is never
prerendered and the boundary is only crossed on a real signed-in request —
which cannot happen locally without Supabase credentials.

That is the same gap that has now hidden three production faults. The dashboard
needs to be runnable locally against a real database before the next phase.

# Fix — the questionnaire crashed on submit

"A 'use server' file can only export async functions, found object."

`programs/actions.ts` exported `initialProgramState` beside its two actions. A
file-level `"use server"` module may only export async functions, and the
violation is not a build error — it throws when the module is first evaluated
on a request.

`lib/messages.ts` already carries a comment explaining this exact rule, written
when the contact form hit it. The codebase knew, and I broke it anyway.

Moved to `lib/programs/form-state.ts`, following that precedent.

## The guard

Two production 500s in a row from boundary rules, neither caught by the build,
the linter, or a hundred tests. Both are runtime faults that surface only when
a module is evaluated on a real signed-in request — which cannot happen here.

`lib/boundaries.test.mts` checks the source statically:

  - a "use server" file exports only async functions
  - a "use client" file does not import a "server-only" module
  - no client component is handed a program template

Verified by breaking it deliberately: adding `export const BROKEN = {}` to the
actions file fails the first check with the file and symbol named. Restored,
and it passes.

The second check needed narrowing during writing. It first flagged
`company-form.tsx` importing `@/lib/companies`, which is `import type` and
therefore erased — a false positive. A guard that cries wolf gets deleted
rather than fixed, so it now ignores type-only imports, including inline
`{ type X }`.

None of this replaces running the app. It is the cheapest thing that would have
caught both faults, and it runs everywhere.
