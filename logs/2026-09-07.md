# 2026-09-07

## Directory badge (task 062)

Added the SaaS Browser listing badge to the footer, in the bottom row opposite
the copyright line. That row was already a single line of small print, so the
badge sits where attribution-shaped things belong rather than competing with
the nav or the ISN/Avetta disclaimer.

The artwork is served from `/public` rather than the issuer's CDN. It is a
12KB SVG with the wordmark baked in as a base64 raster, so proxying it costs
every visitor a third-party connection and hands the issuer a view of our
traffic, for no benefit. What the directory verifies is the outbound link, and
that is untouched. The trade-off is real and worth writing down: if they
update the artwork, ours does not follow.

## Platform audit

Before doing any of the work below, I read the tree rather than the roadmap —
migration files, requirement rows, env reads, test files — and framed the
result as the ten things a contractor has to do in a row. Six worked, three
under-delivered, three did not exist, and the three that did not exist were
all clustered at the end, which is the half that gets paid.

Two findings drove the rest of the day:

- Nothing in the product recorded what anyone had been quoted or agreed to.
- The reference data has twelve rows and every one is `trades: "all"`,
  `platforms: "all"`, so the trade × platform promise has nothing behind it.
  Not addressed today — it is content research, not engineering, and it is
  the single highest-leverage thing left.

## The money path (task 063)

Quoting, accepting, declining and being paid are now **events**, not columns.
The obvious implementation — a `quoted_amount` column and an `accepted`
boolean — would have reintroduced exactly the bug task 055 was written to
remove. A quote is not a property of a request; it is something that happened
to it, on a date, by somebody, and often more than once. A revised price is a
second quote, not an edit of the first, and editing in place would lose the
change that a customer is most likely to query.

So migration 0010 adds two amount columns and four kinds, with a database
constraint that an amount may exist **only** on a quote — otherwise a reply
could carry a number that no screen reads and no state reacts to, sitting in
the table looking authoritative.

An operator can now send a price, record a payment, and set a plan. That last
one is the write 0007 designed for and nothing ever performed: granting
somebody the thing they just paid for was a SQL-editor task until today. It
reports when no company profile matched rather than silently changing nothing,
because "I told them they were upgraded and they weren't" is the failure that
costs a customer.

The customer sees the price in their thread and accepts or declines in one
click. Acceptance is re-derived from the log on the server, so a price that
has been withdrawn, revised, or already answered in another tab cannot be
accepted from a stale page — the one mistake here that costs real money to
unpick.

Eleven new tests, all negative. The two worth naming: **acceptance is not
payment**, and **the agreed price is the one that was accepted, not a later
revision**. Both describe screens that would look completely reasonable and be
wrong about money.

## Six sections became three

The workspace nav was Overview / Requests / Documents / Programs / Company /
Ask for help. Two of those pairs were one idea each:

- The documents page already listed generated programmes above uploaded
  files. A subcontractor does not hold "documents" and "programs" as separate
  things — they hold paperwork. Now one section, and `/dashboard/programs` is
  what it always was: the thing you click to start one.
- Asking for something and watching what you asked for are one activity. The
  help page already rendered the request list a second time, and its copy of
  it was not even clickable — so the more natural page to land on was the one
  that could not open a conversation.

Company left the nav for the header. It is filled in once and then almost
never revisited, and a permanent slot implies attention it does not need.

I also removed the four-figure tile row from the overview, which **reverses a
deliberate decision in task 056**. The reason is what it looked like against
real rows rather than fixtures: two of the four tiles rendered as an em dash,
so half of the most prominent element on the page was a person's first
impression of their own file saying nothing. The other two counted things
listed directly beneath them. What survives is the only figure that asks for
anything — requests waiting on the customer, and only when there are any.

## Defects that only real data showed

Both found by signing in against the live database, which is a thing this
project had never once done for these screens.

- A generated document whose template no longer exists rendered its **raw
  id**. A real customer library was showing `personal_protective_equipment`
  as the name of a document. The row has to stay — the file downloads fine —
  so it needed a name a person would recognise, not removal.
- The same file name appears legitimately several times, once per request, and
  four identical rows read as a bug. Naming the request each came in on
  separates them without hiding any, which deduplicating would.

## Two traps in the setup

- `DEPLOY.md` stopped at migration `0004` while the repo carried `0009`.
  Following the runbook produced an application that compiled, deployed, and
  failed the first time anyone signed in. It now lists `0001`–`0010` with what
  each one is needed by.
- `.env.local.example` was missing **every** SMTP variable while the code read
  them. Sign-in is a magic link, so an environment built from the template had
  no working sign-in and no obvious reason why — every send is a silent no-op
  by design. Audited: every env var the code reads is now in the template.
